# Chat-driven Goal and Task Ledger\n\nSupabase is the persistent data store. ChatGPT conversations are the orchestrator and worker agents. The user starts worker chats manually; GitHub Actions does not spawn ChatGPT conversations.\n\n## Compute boundary\n\n- ChatGPT conversations: interpret goals, plan/decompose work, execute reasoning/tool actions, and independently verify results.\n- GitHub Actions: repository-side CI, builds, tests, validation, and finite GitHub-hosted jobs.\n- Supabase: persistent reads/writes for goals, tasks, subtasks, loop contracts, claims, leases, iterations, evidence, and results.\n- Supabase Edge Functions: not used.\n- PostgreSQL RPCs: only atomic database transactions (goal-scoped FOR UPDATE SKIP LOCKED claims, lease updates, and task-tree writes). No application orchestration or model execution.\n\n## Chat workflow\n\n1. The first ChatGPT conversation is the orchestrator. It creates a uniquely named goal with full context, instructions, and acceptance criteria using goal_ledger_create.\n2. It decomposes the goal into tasks/subtasks. Every task is a Loop Generator contract stored in tasks.loop_definition, with input/output contracts, cycle, evaluation, revision policy, evidence requirements, max iterations, and stop conditions.\n3. It persists the tree with task_ledger_create_tree, assigning goal_id to the root; descendants inherit it.\n4. It reads goal_ledger_summary and reports claimable, blocked, and completed tasks, plus the recommended number of worker chats.\n5. The user manually opens those ChatGPT conversations and says: “Claim a task from goal <goal name>.”\n6. Each worker resolves the exact goal name with goal_ledger_get, then calls task_ledger_claim_goal_next with a unique conversation-scoped agent_id, name, role, capabilities, and lease duration. FOR UPDATE SKIP LOCKED prevents two chats from claiming the same live task.\n7. Each worker reads the full task contract and executes its loop until acceptance criteria are evidenced, a stop condition occurs, or the task is genuinely blocked. Each iteration is persisted.\n8. The worker submits its result. The orchestrator or a separate verifier conversation independently checks evidence, accepts/rejects the result, and updates the parent summary.\n9. A later chat resumes by goal name without access to the original conversation.\n\n## Direct Supabase connector usage\n\nChatGPT conversations use the user's already-connected Supabase connector directly for SQL/RPC and data reads/writes. They do not call the task-ledger Edge Function and do not need separate Supabase Auth users for each browser chat. Give each chat a unique agent_id (for example, chat-orchestrator-<short-id> or chat-worker-<short-id>) and pass it to task RPCs. The connector's project-level access is trusted; never expose service-role credentials in prompts or repository files.\n\nThe standalone CLI/runner path is separate: runner/task-ledger.mjs authenticates with a Supabase JWT and uses /auth/v1/user, /rest/v1 table endpoints, and /rest/v1/rpc functions. It never calls /functions/v1/task-ledger and requires an enabled agent_registry row.\n\n## Goal/task RPCs\n\n- goal_ledger_create: create the persistent goal and initial version/event.\n- goal_ledger_get: retrieve a goal by exact name or UUID.\n- goal_ledger_summary: return task progress and recommended worker count.\n- goal_ledger_update: version and update goal context/status.\n- task_ledger_create_tree: create nested task definitions in one transaction.\n- task_ledger_claim_goal_next: atomically claim one eligible task from a named goal.\n- task_ledger_heartbeat_claim: renew a task lease.\n- task_ledger_record_iteration: append loop input/output/observations/evidence.\n- task_ledger_submit_result: submit a worker result.\n- task_ledger_verify_result: independently verify or reject a result.\n- task_ledger_finalize_parent: finalize a parent only after all children are verified.\n\n## Loop completion rule\n\nA task is not complete merely because a worker says it is complete. It must run its stored Loop Generator contract, record meaningful iterations and evidence, satisfy every acceptance criterion, and pass independent verification. A failed criterion causes another loop cycle when the revision policy permits it; a real permission/dependency blocker is recorded and escalated rather than disguised as completion.\n
