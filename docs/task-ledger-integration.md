# Chat-driven Goal and Task Ledger\n\nSupabase is the persistent data store. ChatGPT conversations are the orchestrator and worker agents. The user starts worker chats manually; GitHub Actions does not spawn ChatGPT conversations.\n\n## Compute boundary\n\n- ChatGPT conversations: interpret goals, plan/decompose work, execute reasoning/tool actions, and independently verify results.\n- GitHub Actions: repository-side CI, builds, tests, validation, and finite GitHub-hosted jobs.\n- Supabase: persistent reads/writes for goals, tasks, subtasks, loop contracts, claims, leases, iterations, evidence, and results.\n- Supabase Edge Functions: not used.\n- PostgreSQL RPCs: only atomic database transactions (for example, goal-scoped FOR UPDATE SKIP LOCKED claims and claim-token-guarded updates). No application orchestration or model execution.\n\n## Goal workflow\n\n1. The first ChatGPT conversation acts as orchestrator.\n2. It creates a goal with a unique name and ID, complete context, instructions, and acceptance criteria using goal_ledger_create.\n3. It decomposes the goal into tasks/subtasks. Every task is a Loop Generator contract stored in tasks.loop_definition.\n4. It persists the tree with task_ledger_create_tree, assigning goal_id to the root; descendants inherit it.\n5. It reads goal_ledger_summary and reports claimable, blocked, and completed tasks, plus the recommended number of worker chats.\n6. The user manually opens those ChatGPT conversations and says: “Claim a task from goal <goal name>.”\n7. Each worker resolves the exact goal name with goal_ledger_get, then claims one eligible task with task_ledger_claim_goal_next. The claim is atomic, so concurrent workers cannot claim the same live task.\n8. Each worker reads the complete task contract and runs its loop until acceptance criteria are evidenced, a stop condition occurs, or the task is genuinely blocked. Every iteration is persisted.\n9. The worker submits its result. The orchestrator or a separate verifier conversation independently checks evidence, accepts/rejects the result, and updates the parent summary.\n10. A later chat resumes by goal name without access to the original conversation.\n\n## Database access\n\npublic.agent_registry maps an authenticated Supabase user to an agent identity and capabilities. Goal/task rows are owner-scoped by RLS. Do not use a service-role key in prompts, runtimes, the public repository, or task records.\n\nrunner/task-ledger.mjs authenticates with the supplied access token and calls /auth/v1/user, /rest/v1 table endpoints, and /rest/v1/rpc functions directly. It must never call /functions/v1/task-ledger.\n\n## Goal and task operations\n\n- goal_ledger_create/get/summary/update: persist and resume named goals.\n- task_ledger_create_tree: create nested tasks in one transaction.\n- task_ledger_claim_goal_next: atomically claim one eligible task from a specific goal.\n- task_ledger_heartbeat_claim: renew a task lease.\n- task_ledger_record_iteration: append loop input/output/observations/evidence.\n- task_ledger_submit_result: submit a worker result.\n- task_ledger_verify_result: independently verify or reject a result.\n- task_ledger_finalize_parent: finalize a parent only after all children are verified.\n\nEvery task requires a Loop Generator contract: objective, input/output contracts, ordered cycle, evaluation method, revision policy, evidence requirements, finite maximum iterations, and explicit success/failure/escalation stop conditions. A task is not complete merely because a worker says it is complete; acceptance criteria must be verified.\n\n## Runner configuration\n\nSet SUPABASE_URL, SUPABASE_ANON_KEY, and SUPABASE_AGENT_JWT for CLI/worker-runtime use. The runner resolves the current user's enabled agent registration and calls PostgREST/RPC directly. It never needs a service-role key and never calls an Edge Function.\n\n## Operational limits\n\nGitHub Actions compute is separate from manually opened ChatGPT conversations. GitHub-hosted CI can build/test repository code, but cannot create or control ChatGPT browser conversations. Supabase stores durable coordination state and performs only minimal atomic transactions needed for consistency.\n
